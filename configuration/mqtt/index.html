MQTT Configuration

BlazeBee speaks MQTT 3.1.1 through the rumqttc client. All settings live under [transport].

Status topic and last will

Section titled “Status topic and last will”

On every successful connection the agent publishes online (retained, QoS 1) to <base_topic>/status. The CONNECT packet carries a last will that publishes offline to the same topic if the connection drops without a DISCONNECT; a clean shutdown publishes offline itself. Subscribe to this topic to distinguish an idle agent from an unreachable host.

TLS

Section titled “TLS”
  • TLS is used when enabled = true or when ca_cert_path is set.
  • Without ca_cert_path, the broker certificate is verified against the system trust store (SSL_CERT_FILE in the container image).
  • ca_cert_path points to a PEM bundle for private CAs.
  • client_cert_path and client_key_path (unencrypted PEM) enable mutual TLS and must be set together. All files are checked at startup.

TLS handshake failures are treated as unrecoverable: the process exits with status 1 rather than retrying with a configuration that cannot work.

Serialization and compression

Section titled “Serialization and compression”

gzip reduces the larger payloads (vmstat, netstat) by roughly 80 %; on an aarch64 server core it costs about 110 µs for a 7 KB message, zstd about 35 µs with a similar ratio.

MessagePack uses positional (array) encoding of structs; CBOR encodes structs as maps keyed by field name. MQTT 3.1.1 has no content-type metadata, so consumers must know the configured format and compression.

Framing

Section titled “Framing”

When enabled, every payload is split into frames that fit max_packet_size. Each frame starts with a 21-byte header: magic FR, version 1, format (0 json, 1 msgpack, 2 cbor), QoS, a 64-bit stream id, a 32-bit frame index and the 32-bit frame count, all big-endian. Frames are published to the sample’s topic in order. Leave this off unless the consumer reassembles frames; with it on, even a small payload carries the header.

Connection behaviour

Section titled “Connection behaviour”
  • Reconnection: after a lost or refused connection the agent waits 1 s, then doubles the delay up to 60 s, with ±20 % jitter, and keeps retrying for as long as the process runs. A successful connection resets the delay.
  • Fatal errors: bad credentials (BadUserNamePassword, NotAuthorized), rejected protocol version or client id, TLS errors and local permission problems stop the process with exit status 1. Under systemd this triggers Restart=on-failure.
  • While disconnected: no samples are taken. Publishes that were already queued are retransmitted after reconnect according to their QoS and the session setting.
  • Shutdown: offline is published, DISCONNECT is sent and the process waits up to 3 s for the broker to take it.

Example with a private CA and credentials

Section titled “Example with a private CA and credentials”

Run with MQTT_PASSWORD in the environment. systemd units can supply it through EnvironmentFile= or a credential; containers through -e or a secret mount.
